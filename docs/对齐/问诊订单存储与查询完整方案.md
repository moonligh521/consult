# 问诊 / 订单存储与查询完整方案

> 产品：在线问诊的智能挂号  
> 容量目标：日均约 10 万轮咨询  
> 体验：患者可回看约 1 年内问诊；管理端时间窗分页；订单号可追溯  
> 原则：**短期分区 + 索引表；长期按会话 id 分库分表；主数据只存一份，列表靠瘦索引**

---

## 1. 诉求与查询路径

| # | 诉求 | 查询键 | 数据落点 |
|---|---|---|---|
| ① | 打开某一次问诊（聊天/卡片/订单） | `consultation_id` | 会话分片上的主表 |
| ② | 患者「我的咨询」近 12 个月列表 | `account_id` + 时间 | `consult_session_index` |
| ③ | 管理端分页列表 | 时间窗 + 筛选 + page | 管理索引 / 同索引表 |
| ④ | 订单号精确追查 | `order_id` | 订单表或 `order → consultation` 路由后再进分片 |

「共 N 条 / 共 M 页」= **当前筛选条件下的总数**，不是全库历史。

---

## 2. 总体架构

```text
写入
  主数据（一份）── hash(consultation_id) ──► 会话分片
       │                                    ├ consultation_session
       │                                    ├ consultation_message   (+ 月分区)
       │                                    ├ consult_order          (+ 月分区)
       │                                    ├ safety_decision_audit  (+ 月分区)
       │                                    └ consult_match_decision (+ 月分区)
       │
       └─ 瘦索引（摘要）──► consult_session_index
                            · 患者侧可按 account_id 分片或先单库
                            · 管理侧同一张或 admin 投影，强制时间窗

读取
  详情 / 锁行     → consultation_id → 单分片点查
  我的 12 个月    → account_id + created_at → 索引表分页
  后台列表        → from/to + 筛选 → 索引表分页（默认 7 天，最长 1 年）
  订单号          → order_id → 定位 consultation_id → 分片详情
```

**不是**一条业务数据完整存三份；是 **1 份主数据 + 1～2 行列表摘要**。

---

## 3. 留存策略

| 层级 | 范围 | 内容 |
|---|---|---|
| 热库在线 | 约 **13 个月** | 会话、消息、订单、审计、索引（可看近 1 年） |
| 订单近线归档 | **≥ 10 年**（财务口径） | 订单关键字段；单号可查，不要求高性能列表 |
| 消息/审计冷归档 | 超 13 个月 | 按月整分区迁出；默认列表不展示 |

患者端列表默认：`created_at >= now() - 1 year`。  
管理端列表默认：近 7 天；可选拉长，**上限 1 年**；禁止无时间条件全表扫。

---

## 4. 分片与分区（两层，别混）

### 4.1 分区（MySQL 能力，短期就上）

- **谁做**：DDL 配置；引擎执行裁剪与存储；应用仍用原表名。  
- **维度**：**时间（按月）**。  
- **表**：`consultation_message`、`safety_decision_audit`、`consult_match_decision`、`consultation_session`、`consult_order`。  
- **运维**：每月预建下月分区；归档后 `DROP` 超 13 个月分区。  
- **不用** ShardingSphere 做分区。

### 4.2 分库分表（长期水位到了再物理拆）

- **维度**：**`consultation_id` hash**，不是按月分表，也不是用户 id 做主分片。  
- **公式**：`shard = hash(consultation_id) % N`  
- **同片表**：session / message / order / audit / match_decision（同一咨询不跨片）。  
- **中间件**：物理多库时用 ShardingSphere-JDBC（或同类）做路由。  
- **每个分片内部**：仍可继续 **按月分区**。

### 4.3 索引表（服务列表）

- `consult_session_index`：列表专用瘦表。  
- 患者列表量大后再按 **`account_id` hash** 拆索引；与会话分片键不同，只存摘要。  
- 管理列表：同一索引 + 时间窗；或只读从库 / 后续 ES（报表重了再上）。

---

## 5. 表设计要点

### 5.1 主表补齐

`consultation_session` 增加：

- `account_id`：开聊写入登录账号（现状缺口，否则无法服务端列「我的记录」）

### 5.2 索引表 `consult_session_index`

| 字段 | 说明 |
|---|---|
| `consultation_id` | PK |
| `account_id` | 患者账号 |
| `order_id` | 可空 |
| `title` | 列表标题（主诉摘要） |
| `business_status` | 业务状态 |
| `patient_name` / `specialty` / `doctor_name` | 展示用 |
| `created_at` / `updated_at` / `ended_at` | 时间与结束 |

索引建议：

- `(account_id, created_at DESC)` — 患者列表  
- `(created_at)` / `(ended_at)` — 管理时间窗  
- `(order_id)` — 订单号反查  

### 5.3 订单

- 保持现有 `consult_order`（含 `ended_at` / `end_reason`）。  
- 长期：热库 13 个月；更早进订单归档库，**单号仍可查**。

---

## 6. 写入时机

| 事件 | 主数据 | 索引 |
|---|---|---|
| 新建咨询 | insert session（带 account_id） | insert index |
| 出卡 / 改主诉 / 确认 | update session | update title/status |
| 下单派医生 | insert/update order | update order_id、doctor、specialty |
| 结束问诊 | order.ended_at + end_reason | update ended_at |

主路径失败要可补偿（本地消息表或定时对账），避免只有会话没有索引。

---

## 7. API

### 患者

```text
GET /api/consultations?from=&to=&page=&size=
GET /api/consultations/{id}
```

- 未传时间：默认近 1 年。  
- 鉴权：仅本人 `account_id`。  
- 响应：`{ total, page, size, items }`。

### 管理

```text
GET /api/admin/consultations?from=&to=&status=&keyword=&page=&size=
GET /api/admin/orders/{orderId}
```

- 未传时间：默认近 7 天；`to - from` 最长 1 年。  
- `total` = 筛选结果集大小。  
- 订单号接口：精确一条；热库未命中再查归档。

废弃：管理端一次拉全量、患者端 localStorage 当主存储。

---

## 8. 分页规则（对齐 HIS 习惯）

- 先定时间范围，再分页。  
- 展示「共 N 条 / 共 M 页」，N 为当前条件。  
- pageSize：患者 20；管理 20/50。  
- 订单号查询不走列表分页。  
- 条件过大时提示缩小时间范围（可选）。

---

## 9. 分期落地

| 期 | 内容 | 备注 |
|---|---|---|
| **P0** | session 补 `account_id`；建 `consult_session_index`；患者记录改服务端；管理端时间窗 + total 分页 | 立刻可做 |
| **P1** | 管理端订单号精确查；结束态写入索引；去掉 localStorage 主依赖 | |
| **P2** | 大表按月分区；13 个月归档作业 | 短期扛量 |
| **P3** | 按 `consultation_id` 物理分库；索引可按 `account_id` 拆；引入 ShardingSphere | 水位到了再上 |
| **P4** | 订单十年近线归档 | 财务合规 |

**P0～P2 即按分片键约束编码**（只用 consultation_id 点查主数据、列表走索引），避免日后洗数推倒重来。

---

## 10. 容量粗算（日均 10 万咨询）

| 表 | 约年增量 |
|---|---|
| session | ~3600 万 |
| order（半转化） | ~1800 万 |
| message | ~1～3 亿 |

- 满一年：通常先要 **分区 + 归档**，不是日历一到就必须分库。  
- 分库水位：热库磁盘/备份/写入 QPS/复制延迟顶不住时再 P3。

---

## 11. 明确不做

- 用「每月一张业务表」替代 MySQL 分区。  
- 用用户 id 作为消息/订单主分片键。  
- 无时间条件的全历史管理列表。  
- 结束问诊立即迁走一年内仍需展示的数据（造成热冷双查）。  
- 完整聊天记录为三种查询各存一份。

---

## 12. 与现状差距

| 现状 | 目标 |
|---|---|
| 患者记录在浏览器 localStorage | 服务端 index + account_id |
| 管理端 `listRecent` 近似全量 | 时间窗 + 分页 total |
| 无分区 | P2 上月分区 |
| 无分片路由 | P0 起访问约束；P3 物理拆 |
| 有 ended_at / end_reason | 保留，索引同步结束态 |

---

## 13. 一句话

**主数据按会话 id（日后 hash 分片），内部按月分区归档；列表靠账号维瘦索引 + 时间窗分页；订单号单独点查并可长期归档。短用分区扛，长用分片扩，查询三条路径各走各的，不靠一份数据切三刀。**
