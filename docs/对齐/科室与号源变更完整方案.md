# 科室 / 号源变更完整方案

> 产品：在线问诊的智能挂号  
> 背景：运营会新增、停用一级类和二级挂号科；医生、排班、在途卡片必须跟着收敛  
> 原则：**目录是资源根；启用才可匹配；停用不打断已支付问诊；号源用目录 JOIN，不另做一份开关**

---

## 1. 现在缺什么

agent 与 identity **共用** `consult_agent` 库，但目录、医生、前端是三份静态拷贝：

| 资源 | 今天怎么活 | 变更时 |
|---|---|---|
| 一级类 `consult_department.enabled` | 快照丢掉停用行；确认走 `requireEnabled` | 有写库方法，**没有管理端接口** |
| 二级科 `consult_department_specialty` | 无 `enabled`；身份靠 `(一级码, 名称)` | 增删只能改 SQL |
| Java `Department` 枚举 | 写死 1–22，`fromCode` 未知即抛 | 新一级加不进去 |
| 患者端 `DEPARTMENT_TREE` | 前端静态文件 | 库改了页面仍是旧树 |
| 演示医生 `demo-specialties.json` | 启动按 JSON 补 ≥2 人 + 近 7 天班 | 新二级 0 医生，支付 `DOCTOR_UNAVAILABLE` |
| 在途 `card_json` / 订单 | 存当时的一级码 + 二级名 | 不停、不改派、不提示过期 |

停一级之后：**新主诉**不再挂该科（落到全科）。  
新增一级/二级、停二级、医生号源、选科弹层、已出卡确认，**都没有闭环**。

## 2. 总体架构

```text
运营在管理端改目录
        │
        ▼
 CatalogChangeService（agent）
        │  同一请求内
        ├─ 写 consult_department / specialty / keyword
        ├─ 延时双删 Redis 目录快照（已有 DepartmentCatalogWriter）
        ├─ 调 identity：覆盖率校验 / 演示补医生
        └─ 记 consult_catalog_change（影响面快照）
                │
                ├──────────────► 匹配：只读 snapshot.enabled ∧ specialty.enabled
                ├──────────────► 派医生：listOnDuty JOIN 开通目录
                ├──────────────► 患者选科：GET /api/departments（开通树）
                └──────────────► 在途：读时校验；已支付不打断
```

**不是**改一行 `enabled` 就算变更。一次变更要同时保证：

1. 新咨询按新目录挂科；  
2. 该科能派到人（或根本不允许开通）；  
3. 未支付卡片不能确认已停的科；  
4. 已支付问诊继续跑完；  
5. 患者端 / 医生端看到的树与库一致。

identity 不要反向写目录。目录只在 agent 写；医生表只在 identity 写。两边用**同一库 JOIN** 对齐，不引入消息队列。

## 3. 资源图与身份键

挂号挂的是 **二级科**，一级只是分类。

```text
一级类 (code, 永不复用)
  └── 二级科 (id 稳定, name 展示)
        ├── 关键词 / 病名 / 同义规则
        ├── 医生 (department_code + specialty_id)
        │     └── 排班 → 占坑 occupancy
        └── 会话卡片 / 订单（存当时快照，不随目录改写）
```

| 对象 | 稳定键 | 展示名 | 说明 |
|---|---|---|---|
| 一级 | `code` INT | `name` | 启用后禁止改号、禁止复用停用号 |
| 二级 | `id` BIGINT（已有主键） | `name` | 匹配、医生、关键词改挂 `specialty_id` |
| 医生 | `consult_doctor.id` | 姓名 | 绑定 `specialty_id`；`specialty` 名作冗余展示 |
| 历史卡片/订单 | 当时的 code + 二级名 | 原文 | **不回写**；回看永远显示当时挂的科 |

二级禁止只靠名称当主键：改名会把医生、关键词、卡片对不上。名称可改，id 不改。

## 4. 生命周期

```text
新建 ──► 停用(草稿) ──► 开通 ──► 停用 ──► 再开通 …
              ▲                      │
              └──── 补医生 / 改词 ────┘
```

- 新建一级、二级默认 **`enabled=0`**，不进匹配、不进患者树。  
- **开通**才是对外生效。开通有门禁（§6）。  
- **停用**立刻从匹配和选科消失；数据保留；医生档案不停删。  
- **物理删除不做**。`is_deleted` 仅留给名称唯一键回收这种仓储细节，运营界面不提供删除。  
- 全库必须永远有且仅有一个 `fallback=1` 的开通一级，且名称固定为 **全科**。停用全科或把兜底改成别的科，直接拒绝。

一级 `enabled` 与二级 `enabled` **独立**：

- 匹配 / 选科 / 派诊：两者都为 1 才算出诊科。  
- 停一级 **不改** 二级的 `enabled`，再开通一级时原来开着的二级自动回来。  
- 一级下没有开通二级时，患者树不展示该一级；也不允许开通一个「空一级」。

## 5. 在途会话（按状态，不扫全表改卡片）

不批量 `UPDATE card_json`（日后日均 10 万做不起）。**读、确认、下单时懒校验**。卡片带 `catalogVersion`（快照 version 字符串）便于排查，不是强校验键。

| 会话状态 | 科被停用之后 |
|---|---|
| 问诊中、未出卡 | 下一句按**新快照**重算。停用科不会再被规则/模型挂上。 |
| `CARD_READY` 未确认 | `GET`/`PATCH` 若当前二级已停：卡片标记 `stale=true`，文案「该科室已停诊，请改科或继续对话重新分诊」。**确认接口拒绝**（1119）。旧卡没有 `specialtyId` 时，用当时的一级码 + 二级名对开通目录。 |
| `CONFIRMED` 未支付 | 改科仍可；**下单/演示支付拒绝**已停二级。可改挂其他开通科后再付。 |
| 已支付 / 占坑中 | **不打断、不改派、不释放号**。医生继续看完。超时收割、手动结束逻辑不变。 |
| 结束 / 历史回看 | 展示下单时快照科名。目录里已停也不改历史。 |

已支付后的 **换医生**（`reassign`）：仍按**原二级**找人。该科医生因目录停用全部 JOIN 不上 → 沿用现有「无医生立刻失败 / 转人工」，**禁止**悄悄改挂全科。患者已经为那个科付过费。

模型若仍吐出已停科名（旧 prompt 缓存等）：路由层当无效，走兜底全科。开通快照本身不含停用科，正常路径不会发生。

## 6. 开通门禁（覆盖率）

产品已有约束：**每个开通二级至少 2 名出诊医生，且有当日可约排班**。

开通二级 `enabled=0 → 1` 时，agent 调 identity：

```
GET /internal/doctors/coverage?specialtyId=
→ { doctorCount, onDutyToday, remainSlotsToday }
```

| 条件 | 结果 |
|---|---|
| `onDutyToday ≥ 2` 且当日剩余号 > 0 | 允许开通 |
| 不足，且 `consult.catalog.provision-demo=true`（当前演示默认 true） | identity 按现有姓名池补人 + 补近 7 天班，再开通 |
| 不足且不允许演示补人 | 拒绝：`SPECIALTY_NO_COVERAGE`（新错误码），返回缺口 |

开通一级：该一级下 **至少 1 个已开通二级**，否则拒绝。

演示补人 **只在开通那一刻** 做；日常 `DoctorSeed` 启动改为扫目录开通二级（不再读 `demo-specialties.json`），只补缺口，不覆盖人工改过的医生。

停诊医生（`consult_doctor.status=0`）不计入覆盖率。

## 7. 医生与排班怎么跟

identity **不复制一份科室开关**。`listOnDuty` 增加目录 JOIN：

```sql
-- 派诊候选人：医生出诊 ∧ 一级开通 ∧ 二级开通 ∧ 今日未停班 ∧ 未满负荷
FROM consult_doctor d
JOIN consult_department dept
  ON dept.code = d.department_code AND dept.enabled = 1 AND dept.is_deleted = 0
JOIN consult_department_specialty s
  ON s.id = d.specialty_id AND s.enabled = 1 AND s.is_deleted = 0
JOIN consult_schedule sch
  ON sch.doctor_id = d.id AND sch.visit_date = CURDATE()
 AND sch.stopped = 0 AND sch.remain_num > 0 AND sch.is_deleted = 0
WHERE d.status = 1 AND d.is_deleted = 0 AND d.in_flight < d.concurrent_limit
```

因此：

- 停科后，该科医生 **自动不再被新单抽到**，不必把 `status` 改成停诊。  
- 再开通后，仍是出诊且有班的医生 **立即** 回到号池。  
- 运营手动停诊仍走 `status=0`，与目录无关。  
- **不改、不删历史排班**；管理端列表对「科已停」打标即可。  
- 已有 `occupancy` 不因停科释放。

医生改挂二级（人跟科走）：管理端改 `specialty_id`（一级码随二级走）。进行中占坑仍属于原医生，不把在途单挪到新科。

新建医生：`specialty_id` 必须指向**已存在**的二级（可停用，方便先建人再开通科）。禁止写一个目录里没有的名称。

## 8. 变更操作一览

管理端每次写操作先出 **影响面**，确认后再提交。影响面接口可单独预览。

| 操作 | 允许条件 | 立刻发生 | 不发生 |
|---|---|---|---|
| 新增一级 | 名称不重复；`code = max(code)+1`，跳过曾用号 | 行 `enabled=0` | 不进匹配 |
| 开通一级 | 非空：≥1 开通二级；不是把第二个 fallback 打开 | 进快照分类 | 不改二级 enabled |
| 停用一级 | 不是 fallback 全科；允许其下仍有开通二级 | 匹配/选科消失；新派诊 JOIN 不上 | 不释放占坑；不改卡片 |
| 新增二级 | 父一级存在；同级名称不重复 | 行 `enabled=0`；可先写关键词、先挂医生 | 不进匹配 |
| 开通二级 | §6 覆盖率；父一级若停用则**同事务开通一级**（开通后该一级恰好有 1 个开通二级，满足一级门禁） | 进快照与患者树 | 不改其他二级 |
| 停用二级 | 该一级停完后若再无开通二级，一级对外等同隐藏 | 匹配去掉该科词；确认/下单 1119 | 不删词、不删医生、不打断已支付 |
| 改二级名 | 新名同级不冲突 | 同事务改 `name`；医生冗余名、关键词 `specialty_name` 一起改 | 历史卡片不改 |
| 改关键词 / 同义 | 目标二级必须存在（可停用） | 已有 writer + 双删 | — |
| 一级之间搬二级 | **不做** | 停旧 + 新建 + 医生改挂 | 避免 id 跨父导致审计混乱 |

停用前影响面至少返回：

- 该二级今日 `CARD_READY` / 未支付 `CONFIRMED` 会话数（可按 `card_json` 二级名估，允许近似）  
- 进行中占坑数（`occupancy.status=1` 且医生 `specialty_id` 命中）  
- 出诊医生数、当日剩余号  
- 停完后该一级是否还会留下开通二级；若不会，提示「患者树将隐藏整个一级」

## 9. 数据改动

### 9.1 二级表加开关

```sql
ALTER TABLE consult_department_specialty
    ADD COLUMN enabled TINYINT NOT NULL DEFAULT 1
        COMMENT '1才可匹配、可手选。新建默认0由应用写入'
        AFTER sort_no;
```

已有 137 个二级：存量默认 1，与现在对外行为一致。

### 9.2 医生挂稳定 id

```sql
ALTER TABLE consult_doctor
    ADD COLUMN specialty_id BIGINT NULL COMMENT 'consult_department_specialty.id' AFTER department_code;

-- 按 (department_code, specialty 名) 回填。对不上的医生保持 NULL，listOnDuty 排除，管理端标「未挂目录」
UPDATE consult_doctor d
JOIN consult_department_specialty s
  ON s.department_code = d.department_code AND s.name = d.specialty AND s.is_deleted = 0
SET d.specialty_id = s.id;
```

`specialty` 列保留作展示冗余，改名时一起更新。派诊、覆盖率、管理端筛选一律用 `specialty_id`。

关键词表 `consult_department_keyword.specialty_name` 同样补 `specialty_id`，匹配加载按 id 关联。

### 9.3 变更审计

```sql
CREATE TABLE IF NOT EXISTS consult_catalog_change (
    id             BIGINT       NOT NULL AUTO_INCREMENT,
    action         VARCHAR(32)  NOT NULL COMMENT 'ENABLE_L1 / DISABLE_L2 / RENAME_L2 …',
    department_code INT         NOT NULL,
    specialty_id   BIGINT       NULL,
    before_json    JSON         NULL,
    after_json     JSON         NULL,
    impact_json    JSON         NULL COMMENT '预览的在途/医生/号源',
    created_by     VARCHAR(100) NULL,
    created_at     DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    KEY idx_catalog_change_time (created_at)
) COMMENT='目录变更审计。不含医生档案正文';
```

### 9.4 枚举退居种子

`Department` 枚举保留 1–22 作为**种子别名**（单测、旧 JSON 反序列化）。  
运行时挂科、确认、卡片对外改为：

- `departmentCode: int`  
- `departmentName: string`  
- `specialtyId: long`  
- `specialty: string`（展示）

`Department.fromCode` 对未知码 **不再抛错**；未知码以目录行准。卡片 Jackson 按 int 读 code。新一级 code=23 只要库里有行就能挂号。

`requireEnabled` / `resolveSpecialty`：手选或确认时，二级对不上 **拒绝**（1119），禁止再静默落到「该一级默认二级」——停用呼吸内科后确认旧卡，不能被改成普内科还显示成功。

## 10. 接口

权限：写接口 staff；患者树可登录患者。

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/departments` | 患者/改卡弹层：仅开通一级 + 其下开通二级 |
| GET | `/api/admin/departments` | 管理树：含停用；每科覆盖率（医生数 / 今日可约） |
| POST | `/api/admin/departments` | 新建一级（停用） |
| PATCH | `/api/admin/departments/{code}` | 改名、排序、性别范围、开通/停用 |
| POST | `/api/admin/departments/{code}/specialties` | 新建二级（停用） |
| PATCH | `/api/admin/departments/{code}/specialties/{id}` | 改名、治疗描述、开通/停用 |
| GET | `/api/admin/departments/impact` | `code` + 可选 `specialtyId` + `action` 预览 |
| GET | `/internal/doctors/coverage` | identity：覆盖率 |
| POST | `/internal/doctors/ensure-demo-coverage` | identity：演示补人补班 |

所有目录写走 `DepartmentCatalogWriter.mutate`（先删 Redis → 写库 → 延迟再删）。写失败也安排第二次删，行为与现网关键词/同义一致。

患者确认、改卡、下单在现有接口上增加「当前二级仍开通」校验即可，不单开状态机接口。

## 11. 前端

**患者端**：删掉静态 `departments.js` 作为运行时数据源。启动或进入改科弹层拉 `/api/departments`，Pinia 缓存；目录 version 变化则刷新。无网关失败时不允许用过期树确认（宁可变慢，不能挂到已停科）。

**管理端科室页**：从只读表改为树 + 开通/停用 + 新建。停用按钮先弹影响面（在途卡、占坑、医生、是否掏空一级）。覆盖率不足时开通按钮给出缺口，演示环境提供「补 2 名医生并开通」。

**管理端医生页**：二级下拉来自**全量目录**（含停用，便于先挂人）。科已停的医生行显示「科室停用·不接新单」，与本人停诊区分。

## 12. 缓存与生效窗口

沿用目录延时双删，默认延迟与现网一致（秒级）。窗口内：

- 最多一次旧快照被并发读回填，第二次删除后下次定科必中库。  
- 不在双删里强刷前端；患者下次打开弹层或下次 `GET` 咨询即按新树校验。  
- identity 派诊是即时 JOIN，**无医生侧缓存要失效**。

手工改 SQL 后仍可只调已有 `invalidateEventually()`。正式运营禁止绕过管理端。

---

## 13. 方案取舍（已锁定）

曾考虑三种做法：

1. **只改 SQL + 重启种子**：快，但前端枚举、医生 JSON、在途卡全是洞。否决。  
2. **目录变更发 MQ，医生异步跟上**：开通瞬间可能 0 医生，支付失败；演示环境过重。否决。  
3. **同库、开通门禁、派诊 JOIN 目录、在途懒校验**（本方案）：写路径仍在 agent；医生仍在 identity；不引入中间件；覆盖率卡住「开了却没人」；已支付不被运营误杀。

演示补人是门禁的一条支路，不是生产 HIS 同步。接真实医生主数据时：关掉 `consult.catalog.provision-demo`，覆盖率改为读 HIS 在线人数，目录模型不用改。

---

## 14. 明确不做（本期）

- 真实支付、HIS 医生主数据同步、分库分表  
- 物理删除一级/二级、回收 code 给新科  
- 二级在一级之间搬迁  
- 停科时批量结束问诊、强制退款、自动改挂全科  
- 用消息队列做目录广播  
- 把 `Department` 枚举扩到「运营每加一科就发版」

## 15. 验收

1. 新建一级+二级（默认停用）→ 患者树没有、主诉不会挂上、确认 1119。  
2. 演示开通二级 → 自动补齐 ≥2 医生和当日班 → 主诉能挂上 → 支付能派到该科医生。  
3. 停用二级 → 新主诉不再中该科词（同类主诉进全科或兄弟开通科）→ 旧 `CARD_READY` 确认失败并提示改科 → 已支付会话仍可聊天直到结束。  
4. 停用一级（非全科）→ 其下二级全部从患者树消失 → 医生 JOIN 不上新单 → 再开通一级后，原先开通的二级和出诊医生恢复接单。  
5. 停用全科 → 接口拒绝，快照仍能加载。  
6. 改二级名 → 新匹配用新名；医生列表新名；历史已结束会话仍显示旧名。  
7. 患者端改科弹层与管理端开通集合同步，不再依赖仓库里的 `departments.js`。  
8. 覆盖率不足且禁止演示补人 → 开通失败，目录保持停用。

## 16. 落地顺序

1. 表结构：二级 `enabled`、医生/关键词 `specialty_id`、变更审计；回填。
