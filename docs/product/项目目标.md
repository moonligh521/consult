# 项目目标

目标取自简历中的「智能挂号助手」。本仓库是一个日均十万单的挂号应用，把下面六条做成可运行、可测试的示例，不表示它是某家医院或平台的线上系统。

简历里的导诊准确度、挂号耗时和扣减准确率来自线上流量与标注数据。本仓库没有这些数据，完成标准只看合成用例是否按约定行为通过。病情、科室和号源都使用合成数据，不写入真实就诊人。

## 六项目标

### 1. 多轮导诊与槽位

患者用自然语言描述病情，例如「干咳半年、运动加重」。状态机驱动多轮对话，识别并追问缺失的性别、年龄和病程。一次只追问一个槽位。三个槽位未齐时，不生成咨询卡片。

V0.1 的 [交付基线](V0.1交付基线.md) 和 [一轮咨询](V0.1一轮咨询.md) 是这项的完成标准。

### 2. 分诊与科室匹配

把病情描述变成症状标签，再路由到科室，例如呼吸内科。路由有两条：

- 关键词规则给出可断言的科室
- 向量检索按症状语义召回科室

两条都实现之后，对外推荐科室仍以关键词规则为准。向量检索的结果单独保留，供对照。没有标注集之前，不把向量结果写成准确率。

V0.1 只完成关键词规则。向量检索在出现调用它的代码时再引入。

### 3. 咨询卡片与号源层级

信息齐了之后生成咨询卡片，包含患者画像、病情描述、症状标签和推荐科室。确认前可以修改。确认后按科室推荐三档示例号源：普通、极速、三甲专家。

本仓库不连接真实挂号系统。V0.1 完成卡片的生成、修改和确认。三档号源留到号源能力进入代码时再做。

### 4. 放号并发

放号前用缓存预热承接查询。扣减号源时用 Redis 分布式锁，使同一号源的并发扣减只有一次成功。测试要覆盖并发冲突，证明不会超卖。

这项在号源扣减进入代码时实现，并按 [基础设施](../engineering/基础设施.md) 封装 Redis。

### 5. 订单、扣减与权益的最终一致

用 RocketMQ 事务消息衔接订单生成、号源扣减和权益校验。消费方以唯一流水号做幂等，同一流水号重复投递时不重复扣减、不重复发放权益。

这项在订单链路进入代码时实现，并封装消息客户端。订单和扣减结果写入 MySQL。

### 6. 日均十万单

本项目按日均十万单设计。十万单指患者确认挂号后形成的订单，按自然日统计。

十万单摊到全天约每秒 1.2 单。放号会集中在短时间里，订单写入、号源扣减、Redis 锁和 RocketMQ 消费都要按这个日量留出余量：高峰时同一号源仍然只有一次扣减成功，重复消息仍然不重复扣减。

V0.1 不把十万单压测当作本版验收。号源和订单链路进入代码后，用压测确认能够承载日均十万单。

开展前先遵守 [互联网诊疗服务边界调研报告](互联网诊疗服务边界调研报告.md)。第一阶段按 [合规边界与适用场景评估](AI挂号助手合规边界与适用场景评估.md) 执行：AI 导诊、线下门诊挂号和急症安全分流。互联网复诊和远程会诊不进入第一阶段的自主决策。

## 技术目标

运行时保持 JDK 21 与 Spring Boot 4.1.1。

模型接入按简历使用 LangChain4j 调用 DeepSeek，负责从自然语言里抽出槽位和症状。LangChain4j 的版本和 DeepSeek 的模型名在第一次调用时写入基础设施文档和示例配置。密钥不进入仓库。抽出的结果必须接受第 1、2 项的规则校验。规则实现在没有模型时也要单独通过 V0.1 验收。

MySQL 8.0.46、Redis 8.2.10、RocketMQ 5.5.1（Java 客户端 rocketmq-spring 2.3.6）的版本保持不变。向量库的产品和版本在第 2 项引入向量检索时选定。

用到哪一项，才引用哪一项的依赖。

## 完成顺序

1. V0.1：目标 1，以及目标 2、3 中的关键词科室和咨询卡片。
2. 接入 LangChain4j 与 DeepSeek，抽取结果仍通过同一套槽位和科室规则。
3. 为症状到科室增加向量检索，推荐科室继续以规则为准。
4. 按科室推荐普通、极速、三甲专家三档示例号源。
5. 加上 Redis 锁、缓存预热、RocketMQ 事务消息和唯一流水号幂等。
6. 压测订单链路，确认能够承载日均十万单。
