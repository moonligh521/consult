# 项目目标

本仓库把导诊挂号做成可运行、可测试的示例，不表示它是某家医院或平台的线上系统。

线上流量里的导诊准确度、挂号耗时和扣减准确率依赖标注数据。本仓库没有这些数据，完成标准只看合成用例是否按约定行为通过。病情、科室和号源都使用合成数据，不写入真实就诊人。

本仓库是导诊挂号的 agent 服务。患者描述症状，信息不够则追问，然后推荐科室；后续版本按付费档位匹配医生并创建问诊订单，成功同步到医生端后本服务不再跟问诊。接诊由医生端完成。规则见 [问诊订单与医生派单](问诊订单与医生派单.md)。

开展前先遵守 [互联网诊疗服务边界调研报告](../合规/互联网诊疗服务边界调研报告.md)。第一阶段按 [合规边界与适用场景评估](../合规/AI挂号助手合规边界与适用场景评估.md) 执行：AI 导诊、线下门诊挂号和急症安全分流。互联网复诊不由本 agent 自主开展；问诊订单只作为交给医师的交接单。

实现落点见 [技术设计](../工程/技术设计.md)，测评见 [测评方案](../工程/测评方案.md)。六层架构和状态机见 [风险识别与安全处置规范](../合规/AI导诊风险识别与安全处置规范.md)。大模型负责理解和整理信息，独立规则负责风险拦截，医生端负责接诊，医疗机构依法承担医疗服务和质量安全职责。

## 六层目标

这六层是产品安全分层，和工程里的 Redis、消息队列、压测不是同一套编号。

### 1. 患者入口与知情告知

说明服务身份：整理就医信息、推荐科室候选，不能替代执业医师的诊断。采集个人信息前完成告知和授权。V0.1 不做登录，只在仓库声明里标明服务边界。

### 2. 独立安全分流

危险信号由独立规则判定，优先级高于导诊和预约。安全引擎不可用时，不得把本次请求当成低风险，不得继续普通预约。

V0.1 先识别四个短语：胸痛、呼吸困难、意识障碍、口唇发紫。命中后进入疑似紧急情况，提示拨打 120 或前往最近的实体医院急诊，不追问槽位，不生成咨询卡片。同义说法、特殊人群、人工升级，以及医疗专业人员审核后的完整触发清单，留到后续版本。

### 3. 导诊与信息整理

患者用自然语言描述病情。状态机一次只追问一个缺失槽位，顺序为性别、年龄、病程。三个槽位未齐时，不生成咨询卡片。信息齐了之后抽出症状标签，按关键词规则给出科室候选。

模型接入后只抽取槽位和症状，抽取结果仍须通过本层规则和第 2 层安全分流。本层不得自行覆盖已经触发的高风险状态。向量检索按症状语义召回科室，结果单独保留供对照；对外推荐仍以关键词规则为准。没有标注集之前，不把向量结果写成准确率。

V0.1 完成槽位、关键词科室和咨询卡片。向量检索在出现调用它的代码时再引入。

### 4. 医院与科室匹配

科室、医院、院区、专病门诊、医生资质和就诊规则来自权威目录，不由模型编造。

V0.1 使用固定关键词科室表。后续版本在咨询卡片后进入四档下单页（普通咨询、极速咨询、三甲医生、权威专家），支付成功后立即同步问诊订单。派单策略见 [问诊订单与医生派单](问诊订单与医生派单.md)。医生名单不由模型编造。

### 5. 预约执行与状态核验

用户确认咨询卡片、选定四档之一并支付成功后，本 agent 立即创建问诊订单并同步医生端。只有医生端明确接收成功，才对患者显示已发起咨询。同步失败则回滚或重试，不得假称成功。接收成功之后，本 agent 不再跟接诊、会话和处方。

V0.1 确认咨询卡片后结束，不创建问诊订单，不同步医生端。后续版本用 Redis 分布式锁和放号前缓存预热约束同一医生或同一档位的并发派单；用 RocketMQ 事务消息衔接问诊订单和向医生端的同步，以唯一流水号做幂等，避免重复建单。

本项目按日均十万单设计。十万单指成功同步到医生端的问诊订单，按自然日统计，摊到全天约每秒 1.2 单。放号和派单会集中在短时间里，订单写入、队列匹配、锁和消息消费都按这个日量留出余量。V0.1 不把十万单压测当作本版验收。

### 6. 审计、评测与持续治理

记录状态切换、规则版本、模型版本、人工干预和异常事件。上线前按 [安全测试与上线验收标准](../合规/AI挂号助手安全测试与上线验收标准.md) 单独统计高风险漏识别率和危险性低估率，不用总体准确率代替。规则或模型升级后重新验证。

V0.1 用验收用例锁住急症分流和科室规则。完整审计字段和评测集随后续版本写入。

## 状态机

用状态机执行，不依赖一段提示词。状态 C、D、E 的完整触发条件由医疗专业人员审核，并随接入的医疗机构调整。

| 状态 | 含义 | V0.1 |
| --- | --- | --- |
| A 普通就医需求 | 查询医院信息，或症状未触发更高处置 | `NEED_DESCRIPTION`、`NEED_SLOT` |
| B 预约候选已生成 | 展示真实科室、医生、院区、时间和规则，供用户确认 | `CARD_READY` → `CONFIRMED`。本版确认后不调预约接口 |
| C 需要线下评估 | 停止诊断性判断，提示实体医疗机构或相应就诊方式 | 后续版本 |
| D 疑似紧急情况 | 中止普通导诊和预约，先提示紧急求助 | `URGENT` |
| E 需要人工协助 | 信息矛盾、特殊人群、风险不明确，或用户要求人工 | 后续版本 |

## 技术目标

运行时保持 JDK 21 与 Spring Boot 4.1.1。

模型接入使用 LangChain4j 调用 DeepSeek，负责从自然语言里抽出槽位和症状。LangChain4j 的版本和 DeepSeek 的模型名在第一次调用时写入基础设施文档和示例配置。密钥不进入仓库。抽出的结果必须接受第 2 层安全分流和第 3 层槽位、科室规则。规则实现在没有模型时也要单独通过 V0.1 验收。

MySQL 8.0.46、Redis 8.2.10、RocketMQ 5.5.1（Java 客户端 rocketmq-spring 2.3.6）的版本保持不变。向量库的产品和版本在第 3 层引入向量检索时选定。

用到哪一项，才引用哪一项的依赖。封装时机见 [基础设施](../工程/基础设施.md)。

## 完成顺序

1. V0.1：第 2 层四个急症短语，第 3 层槽位、关键词科室和咨询卡片。完成标准见 [交付基线](V0.1交付基线.md) 和 [一轮咨询](V0.1一轮咨询.md)。
2. 接入 LangChain4j 与 DeepSeek，抽取结果仍通过同一套安全分流和科室规则。
3. 扩展第 2 层：同义说法和医疗专业人员审核后的触发清单；补上状态 C、E。
4. 采集身份或症状用于预约时，补齐第 1 层告知与授权。
5. 为症状到科室增加向量检索，推荐科室继续以规则为准，且不得覆盖第 2 层。
6. 第 4 层：咨询卡片后展示普通咨询、极速咨询、三甲医生、权威专家四档下单页。
7. 第 5 层：创建问诊订单并同步医生端；加上 Redis 锁、缓存预热、RocketMQ 事务消息和唯一流水号幂等。对端接收成功后本 agent 结束该单，接诊由医生端执行。
8. 第 6 层：决策记录、规则与模型版本、高风险漏识别率门槛。
9. 压测订单链路，确认能够承载日均十万单。
