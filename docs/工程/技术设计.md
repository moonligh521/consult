# 技术设计

设计日期：2026-10-21。

本文是导诊挂号 agent 的实现依据。产品路径见 [项目目标](../产品/项目目标.md) 与 [问诊订单与医生派单](../产品/问诊订单与医生派单.md)。V0.1 的接口和类落点见 [一轮咨询](../产品/V0.1一轮咨询.md) 与 [V0.1 应用结构](V0.1应用结构.md)。测评见 [测评方案](测评方案.md)。

本仓库不实现医生接诊界面。问诊订单成功交给医生端之后，接诊、会话、诊断和处方在医生端完成。

## 结论

系统拆成两段：

1. **本 agent**：急症分流、多轮补槽、科室候选、咨询卡片；后续版本核验复诊、收款、创建问诊订单，把卡片、档位和派单策略同步到医生端。
2. **医生端**：按同步来的策略接诊、超时换人、只升不降地排队。诊疗过程不回到本 agent。

同步以医生端明确接收为成功。失败不得对患者显示已交给医生。接收成功后，本 agent 不再改派、不再催诊。退款和对账可以接收医生端回执，这不是继续问诊。

## Agent 数量与模式

本仓库一共 **2 个 Agent**。医生端不是本仓库的 Agent。

| Agent | 何时在线 | 职责 |
| --- | --- | --- |
| 导诊 Agent | 服务患者 | 分流、追问、科室卡片；后续版本收款并同步问诊订单 |
| 测评 Agent | 只在离线评测时运行 | 跑测试集、算出安全指标、写出是否允许扩大使用范围 |

模式是 **一个编排器调用多工具**，不是多个 Agent 互相商量，也不是模型自己决定下一跳的自由 ReAct。编排器是 `ConsultationService` 状态机。模型只作为「抽槽位、抽症状」这一个工具，抽完必须再过规则工具。规则工具的结论优先于模型。

```text
患者一句话
    → 导诊 Agent（状态机编排，不是 LLM 循环）
        → 工具 SafetyGate      规则，可一票否决
        → 工具 SlotParser / IllnessExtractor   V0.1 规则；后续模型只抽字段
        → 工具 SymptomExtractor
        → 工具 DepartmentRouter  规则，不能覆盖 URGENT
        → （后续）工具 FollowUpVerifier、Payment、OrderSync
    → 卡片或 URGENT 提示
    → 支付成功则 OrderSync；医生端接诊，导诊 Agent 结束

测评 Agent（离线）
    → 对测试集每一条调用同一套导诊 Agent
    → 对照参考答案计分
    → 输出漏识别率等，不给患者回话
```

V0.1 导诊 Agent 不接大模型，四个工具全是规则。接入 LangChain4j 之后仍是这一个导诊 Agent，只是把 `IllnessExtractor` 换成模型工具，编排顺序不变。

禁止的模式：多个诊疗 Agent 会诊、用一段系统提示词代替状态机、让模型选择跳过 `SafetyGate`、测评 Agent 直接对真实患者说话。

### 工具清单

导诊 Agent 的工具：

| 工具 | 实现 | 可被模型覆盖 |
| --- | --- | --- |
| `SafetyGate` | 规则 | 否 |
| `SlotParser` | V0.1 规则；后续可由 `IllnessExtractor` 补齐后再校验 | 否，校验失败继续追问 |
| `SymptomExtractor` | 短语表，后续模型只提供候选 | 否 |
| `DepartmentRouter` | 关键词表 | 否 |
| `CardReconcile` | 后续，争议追问并回到确认卡片 | 否 |
| `FollowUpVerifier` | 后续，病历核验 | 否 |
| `RecordPrefill` | 后续，经同意把档案字段填进卡片 | 否，且须患者确认 |
| `Payment` | 后续，四档收银台 | 否 |
| `OrderSync` | 后续，同步医生端 | 否 |

测评 Agent 的工具：测试集读取、调用导诊 Agent 的同一套服务方法、对照参考标签、汇总指标、写出报告。不调用 `Payment`、`OrderSync` 的真实医生端。

### 用不用 loop

| 场景 | 用不用 | 怎么用 |
| --- | --- | --- |
| 患者多轮追问 | 用 **状态机循环** | 一次只追问一个槽位，急症立即停。不是模型 while 调工具 |
| 导诊推理 | **不用** LLM ReAct / 自主 loop | 每轮请求走固定工具顺序，跑完即返回 |
| 测评跑测试集 | 用 **有界 for 循环** | 一条用例一次调用，集合跑完停止 |
| 模型或规则升级后回归 | 用 **整轮重跑** | CI 或手工再跑测评 Agent 一遍，不是挂在患者路径上 |
| 线上定时巡检 | V0.1 **不用** | 后续若要定时回归，用 CI 定时任务跑测评批；不用 Cursor `/loop` 服务患者 |

导诊 Agent 没有开放步数的工具循环。测评 Agent 的循环上限等于测试集条数。Cursor 的 `/loop` 只适合开发时催促本地 `mvn verify`，不进入生产编排。

## 记忆、矛盾确认与就诊档案

这三项都要规划，但不都在 V0.1 落地。原则：记住完成本次导诊所必需的信息；有争议就回到咨询卡片让患者确认；历史档案只用于核验和补齐字段，不做诊断性「综合分析」。

### 上下文记忆

记忆分三层，越往后权限越严。

| 层 | 记什么 | 谁读 | 何时做 |
| --- | --- | --- | --- |
| 本轮会话 | 已填槽位、病情原文、症状、推荐科室、卡片修改 | 导诊 Agent 状态机 | V0.1 已规划：`InMemoryConsultationStore`，进程内，重启丢失 |
| 跨会话摘要 | 该就诊人最近科室、未完成卡片、未支付订单 | 导诊 Agent，经授权 | 后续。按就诊人隔离，不把完整聊天记录反复送进模型 |
| 就诊档案 | 该就诊人在实体机构的诊断、病历要点、用药过敏 | `FollowUpVerifier` 等规则工具 | 后续。默认不上传给模型 |

V0.1 只有本轮会话记忆：同一 `consultationId` 下，后一句能看到前一句已经填上的性别、年龄、病程和病情描述。已填槽位不被后续句子悄悄改掉，要改走修改卡片。服务重启后编号失效，没有跨用户记忆。

后续跨会话记忆必须先登录并单独告知。写入的是结构化摘要（科室、档位、订单号），不是把历次对话当成长提示词。模型调用仍只拿当前轮抽槽所需字段。

### 有争议时回到确认卡片

会追问，并且必须让患者再确认卡片。不在争议未解决时支付或同步医生端。

视为争议的情况：

- 前后说法打架，例如先说 20 岁又说 45 岁，或科室与主诉明显对不上。
- 患者改了卡片，新内容与病情原文矛盾。
- 已生成卡片后又补充新症状、新病程。
- 下单过程中断后再回来，卡片可能已过时。

处理顺序：

1. `SafetyGate` 仍最先跑。新内容一旦是急症，进入 `URGENT`，不再纠结卡片。
2. 不是急症，则指出哪一项不一致，一次只问一个争议点。
3. 用患者当轮确认的值更新卡片，状态回到 `CARD_READY`。
4. 患者再次确认卡片后，才能进入四档下单。V0.1 的 `confirm` 就是这张卡的确认；后续支付前若卡片又变，必须再确认一次。

V0.1 已有：`CARD_READY` 之后再发文本返回 `CARD_PENDING_CONFIRMATION`，要求先确认或修改卡片。后续把「争议追问 → 更新卡片 → 再次确认」写成独立工具 `CardReconcile`，仍由状态机调用，不交给模型自行结案。

信息仍无法对齐时，转入需要人工协助，不编造折中诊断。

### 历史就诊档案

后续可以读授权范围内的就诊档案，用途限定为三件：

1. **复诊核验**：有无实体机构明确诊断和病历、是否同一诊断、能否创建互联网诊疗问诊订单。
2. **补齐卡片**：经患者同意，带出姓名、性别、年龄、既往科室，减少重复追问。带出的字段仍显示在卡片上，由患者确认。
3. **同步给医生端**：把患者确认后的卡片和核验结果交给接诊医师。综合病情判断由医生做。

导诊 Agent **不做**基于历次病历的疾病推断、鉴别诊断、疗效评价或「根据档案你应该是某病」。那已经进入诊疗，且处方不得由人工智能生成。档案默认不进入模型上下文；确需抽取时只抽取核验和补卡所需的结构化字段，并留下访问审计。

无档案或患者不同意读取时，仍可做普通导诊和线下挂号推荐，不创建互联网诊疗问诊订单。

## 账号与就诊人

一个登录账号可以绑定多名就诊人，例如本人、配偶、父母、子女。问诊订单、卡片、会话记忆、复诊核验和就诊档案都跟 **当前就诊人** 走，不跟账号混用。

| 对象 | 作用 |
| --- | --- |
| 账号 | 登录、支付、看名下订单。V0.1 无账号 |
| 就诊人 | 实名档案：姓名、证件、性别、年龄关系。一次咨询只选一名 |

规则：

1. 进入导诊前选定就诊人。卡片上的咨询人必须是这名就诊人，下单后不能改成另一人而不重新确认卡片。
2. 本轮会话、跨会话摘要、病历核验按就诊人隔离。不得把 A 的症状写进 B 的订单。
3. 为他人咨询视为代预约：须有该就诊人的绑定关系；不满十四周岁须由监护人账号绑定，并按监护人同意规则处理。儿童急症提示不因绑定未完成而推迟。
4. 四档支付记在账号上，问诊订单仍写就诊人编号，同步给医生端的也是就诊人。
5. 解绑就诊人后，该人未完成的咨询不得继续支付；依法应保留的订单按数据规范留存。

V0.1 不做登录和就诊人档案，咨询卡片里的性别、年龄即当次咨询人画像。后续登录能力引入时再加就诊人列表、绑定、切换和代预约授权。

## 安装与运行

V0.1 本地需要 JDK 21、Maven，以及能访问已有 MySQL 的网络。不安装 Redis、RocketMQ、向量库和模型密钥。

```text
JDK 21
Maven 3.9 或以上
mvn -B verify
mvn -B spring-boot:run
```

服务端口 `18081`。数据源写在 `application.yml`。提交时主机为 `127.0.0.1`，不写真实服务器地址和口令。本机运行把主机改成实际地址，提交前改回 `127.0.0.1`。镜像用 `Dockerfile` 构建。

Redis、Nacos、Mongo：代码用到再接，接到这台已有实例，不另起一套。

后续版本每引入一项能力，按 [基础设施](基础设施.md) 同时补依赖、端口和封装。典型安装顺序：JDK 与本应用（启动已连已有 MySQL）→ 订单表 → 已有 Redis（派单锁与缓存）→ RocketMQ 5.5.1（同步事务消息）→ LangChain4j 与 DeepSeek（抽槽，密钥在环境变量）。医生端是外部系统，本仓库只配置它的接收地址和鉴权。

合并请求在 GitHub Actions 跑 `branch-name` 与 `verify`（`mvn -B verify`）。

## 六层怎么落地

| 层 | 本仓库怎么做 | 医生端 |
| --- | --- | --- |
| 1 入口与告知 | 声明服务身份；采集身份前单独告知。V0.1 不做登录 | 医师账号与执业校验 |
| 2 安全分流 | `SafetyGate` 独立于模型。不可用时不建单、不同步 | 接收后仍可按院内规则拒绝急症单 |
| 3 导诊整理 | 状态机补槽、抽症状、规则推荐科室。模型只抽槽位和症状 | 使用同步过去的卡片，不让模型在本侧继续诊疗 |
| 4 医院科室与档位 | 确认咨询卡片后进入四档下单页 | 按档位供给池接诊 |
| 5 订单同步 | 创建问诊订单，同步医生端，幂等，失败不假成功 | 返回对端订单号；接诊后状态以医生端为准 |
| 6 审计测评 | 记录状态、规则版本、同步结果。测评见 [测评方案](测评方案.md) | 诊疗病历按互联网诊疗规则保存 |

## V0.1 切片

本版只实现第 2 层四个短语和第 3 层槽位、科室、卡片。进程内存会话。包和测试以 [V0.1 应用结构](V0.1应用结构.md) 为准。

请求进入 `ConsultationController`，规则在 `ConsultationService`。顺序固定为：`SafetyGate` → `SlotParser` → `SymptomExtractor` → `DepartmentRouter`。命中急症后状态为 `URGENT`，后面的科室规则不得改回普通导诊。

不创建 `infrastructure` 包，不调用医生端。

## 问诊订单（后续版本）

咨询卡片确认、患者选定四档之一并支付成功后，立即创建问诊订单并同步医生端。急症分流触发则不进入下单页。档位编码、服务形态和退款时限见 [问诊订单与医生派单](../产品/问诊订单与医生派单.md)。

同步给医生端的字段：

| 字段 | 用途 |
| --- | --- |
| `consultationId` | 本 agent 咨询编号 |
| `orderId` | 本 agent 问诊订单号，同步幂等键 |
| `card` | 咨询人、科室、问题描述、症状 |
| `paidTier` | `GENERAL` 普通咨询、`RAPID` 极速咨询、`TERTIARY` 三甲医生、`EXPERT` 权威专家 |
| `sla` | 时长、轮次、接诊后未回复退款时限 |
| `dispatchPolicy` | 公立池只升不降；极速自营池不跨池；同档先到先得 |
| `queueState` | 待同步 / 已接收。接诊医生由医生端回填 |
| `followUpVerified` | 复诊核验结果。互联网诊疗复诊单未通过则不同步 |
| `safetyStatus` | 未触发急症才能同步 |

医生端接收成功后返回 `externalOrderId`。本 agent 保存该号，用于对账和幂等，不再用它推进问诊。同一 `orderId` 重复同步，医生端不得生成第二单。

医生超时未接、换人、升档、排队，都在医生端按 `dispatchPolicy` 执行。本 agent 不在同步后再改这些字段，除非医生端回传「未接诊、需退款」。

实现时增加端口，名称在首次编码时写入 [基础设施](基础设施.md)：

- 问诊订单仓储（MySQL）
- 医生端同步（HTTP 或消息，失败可重试，超时不得记为成功）
- 同步事务消息（RocketMQ，唯一流水号等于 `orderId`）
- 并发锁（Redis，避免同一支付结果写出两单）

业务代码只依赖这些端口。医生端客户端类型留在 `infrastructure`。

## 失败处理

| 情况 | 行为 |
| --- | --- |
| 安全引擎不可用 | 不视为低风险，不生成卡片，不创建问诊订单 |
| 模型超时或无把握 | 不编造科室或医生。V0.1 无模型，规则单独可测 |
| 复诊核验失败 | 可保留科室推荐；不创建问诊订单 |
| 医生端同步超时或失败 | 可重试；患者侧不显示已交给医生 |
| 医生端回传未接诊 | 本 agent 只做退款和对账，不重开诊疗对话 |
| 号源或医师目录不可用 | 不显示已匹配、已同步 |

## 数据与模型

症状按敏感个人信息处理。身份证号、手机号尽量只在创建订单和同步医生端时出现，默认不进入模型，也不写入普通日志。病历和检查报告默认不上传。处理角色、保存期限和跨境限制见 [医疗健康数据与大模型调用合规规范](../合规/医疗健康数据与大模型调用合规规范.md)。

抽取结果必须再过 `SafetyGate` 和科室规则。提示词不能授予「忽略安全规则」的权限。模型名、参数和失败策略见下一节。

## 模型选型

V0.1 **不调用模型**，规则单独通过验收。下面的选型在出现 `IllnessExtractor` 时一次性落地，不再临时换厂商。

| 项 | 选定 | 原因 |
| --- | --- | --- |
| 用途 | 只抽槽位和症状，输出结构化字段 | 编排和急症、科室仍由规则做 |
| 接入库 | LangChain4j，经 `infrastructure.langchain` 封装 | 与系列仓库、简历栈一致 |
| LangChain4j 版本 | JDK 21 可用的 1.x 稳定版 | 写入 `pom.xml` 的当次提交把具体版本号回写 [基础设施](基础设施.md) |
| 对话模型 | DeepSeek 官方 `deepseek-chat`（DeepSeek-V3） | 国内接口；延迟低于 reasoner；不把导诊默认送到境外通用模型 |
| 不用 | `deepseek-reasoner`、多模型会诊、让模型选工具跳转 | reasoner 偏长推理，容易写成诊疗文字 |
| 接口 | `https://api.deepseek.com`，OpenAI 兼容 | 密钥只放环境变量 `DEEPSEEK_API_KEY` |
| 采样 | temperature = 0，短输出，只要 JSON 字段 | 抽取要稳定，不要发挥 |
| 超时 | 单次不超过 8 秒 | 超时则本轮只用规则抽取，不编造 |
| 输入 | 当前轮病情文本和待填槽位 | 不传身份证号、手机号、完整病历 |
| 测评裁判 | 不用第二个大模型打分作为上线门槛 | 对照人工审核的参考集；模型只是被测对象 |

向量检索引入时再定嵌入模型和向量库产品，原则相同：可境内部署、版本写入基础设施表、召回结果不得覆盖 `SafetyGate`。候选在引入当次的提交说明里写明，不在 V0.1 预装。

换模型或升级主版本，必须重跑测评 Agent 的高风险漏识别和危险性低估。未重跑不得扩大真实患者使用范围。
